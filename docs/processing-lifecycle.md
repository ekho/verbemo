# macOS background operation ownership (#42)

`ProcessingOperations.shared` is process-local. CLI instances have their own registry; `SessionClaim` remains the cross-process file owner. No cancel operation sends signals to another Verbemo process.

## Contract for #7 (shutdown)

Close admission synchronously with `closeAdmission()` **before** stopping recording. Recording capture and `LiveTranscriptionCoordinator` remain separately owned real-time services. Stop/finalize capture, then await `finishRecording()` on live recognition. The existing transition may try to enqueue canonical processing afterward; closed admission rejects that request, leaving the finished recording on disk for recovery next launch. Never put capture/live in the processing queue. `finishRecording()` awaits the load and managers it detaches in that call. Temporary live toggles/restarts also launch retirement cleanup from `stopPipeline`; those older task handles are not retained today. #7 must retain/drain those live retirees and await the original stop → live finish → enqueue handoff itself. Calling `finishRecording()` a second time is not a barrier for a handoff already in progress. These live services are outside this registry's completion promise.

From outside an owned operation, await `cancelAllAndWait()`. It closes admission idempotently, requests cancellation of all active runs, and waits for their cleanup. It does not itself stop capture, finish live recognition, handle AppKit termination or install signal handlers; those are #7. It does not reopen admission. A new app process starts with an open registry.

The registry covers queued and direct transcription/diarization, automatic and explicit post-processing/summary, recovery sweep including waiting, import, and recording-only archiving. Existing serial transcription/diarization and import policies remain in their owners. A separate drain entry owns the reusable engine cache and wakefulness hold, preserving model reuse across queued meetings. Nested stages of one meeting reuse their operation; sweep has a parent run plus independently cancellable per-meeting children. A cancelled sweep does not schedule another pass.

## Contract for #30 (Journal cancellation)

`snapshot()` returns immutable snapshots with a run UUID, canonical meeting URL if applicable, kind/stage, and `waiting`, `running` or `cancelling` state. Use a snapshot UUID with `cancelAndWait(id)` to cancel exactly that generation. `cancelAndWait(session:)` takes the matching generations present at the call; it does not target a later run. Repeated cancellation is harmless. Waiting queue reservations can be removed before starting; started work remains visible while unwinding and releasing claims and engines.

Call cancellation/wait methods from an external owner, never from inside the same operation. Awaiting cancellation is cooperative: blocked native inference and synchronous archive conversion must return safely before resources can be freed. No timeout may be reported as successful cleanup. Cancellation preserves finished versions, prior summaries and source audio needed for retry; it does not spend failure attempts. A later explicit request or later recovery may resume the session; cancellation does not immediately requeue it in the current drain.

## Children and shared resources

Native engines keep their current cancellation callbacks and dedicated execution lanes. An operation awaits inference, then engine release, before finishing. Detached audio conversion is awaited even where it cannot stop mid-call. Import forwards cancellation to its hashing and normalization tasks and awaits them before removing staging. LLM command execution uses `Subprocess.run`, which waits for the launched process to exit after terminate/kill and cleans its temporary files; user-supplied `on_stop` commands use the same awaited runner with their original meeting working directory and arguments. The direct command must exit before its operation completes. An accepted hook stays marked fired on cancellation to avoid duplicating external side effects. Its standard input is closed. Awaiting the hook is a deliberate change from fire-and-forget: a long hook holds the session claim and delays the next queued transcription or direct diarization until it exits or is cancelled. A hook that invokes a Verbemo CLI writer for the same meeting receives a busy claim; recording/live and other independent operations remain separate. Command authors own any descendant processes their commands launch; the runner controls the directly launched process, including its terminate/kill/wait sequence. Captured output is bounded by the existing 32 MiB runner limit; output from a cancelled command is not forwarded.

Model stores own shared download flights. Cancelling one operation stops that consumer's wait; it must not cancel downloads still needed by another consumer. A flight with no consumers follows the store's cancellation/cleanup contract; this registry does not take ownership of shared model caches, separately requested settings downloads, calendar/metadata reads, or UI scans. Those do not write a meeting pipeline result and must not be mistaken for an active meeting operation. #7 must separately consider service timers and non-processing UI tasks when coordinating application exit.

Windows ownership is unchanged. This document specifies a foundation; the final exit UI/signals and Journal cancellation UI are separate tasks.
