# macOS background operation ownership (#42)

`ProcessingOperations.shared` is process-local. CLI instances have their own registry; `SessionClaim` remains the cross-process file owner. No cancel operation sends signals to another Verbemo process.

## Contract for #7 (shutdown)

After QuitGate accepts quitting, `AppTermination.begin` synchronously closes admission before stopping services and capture. Menu, Dock and signal exits share AppKit's deferred termination path; repeated requests share one cleanup and one reply. `VerbemoApplication` guards the outer `terminate` entry: AppKit otherwise treats a repeated terminate during its pending reply as an immediate exit without asking the delegate again. Signals schedule the request through the run loop, outside the signal handler's main dispatch drain.

`LiveTranscriptionTransitions` retains and serializes the original begin/toggle/finish/enqueue chain. `LiveTranscriptionCoordinator` retains retired preload, consumer and manager tasks from earlier toggles/restarts. Shutdown awaits that original handoff and all live retirees; a second `finishRecording()` alone is not the barrier. Closed admission rejects canonical processing of the newly saved recording, leaving it on disk for the next process's recovery.

From outside an owned operation, shutdown then awaits `cancelAllAndWait()`. It closes admission idempotently, cancels existing runs and waits for actual cleanup. No timeout establishes cleanup. Admission never reopens in this process.

The registry covers queued and direct transcription/diarization, automatic and explicit post-processing/summary, recovery sweep including waiting, import, and recording-only archiving. Existing serial transcription/diarization and import policies remain in their owners. A separate drain entry owns the reusable engine cache and wakefulness hold, preserving model reuse across queued meetings. Nested stages of one meeting reuse their operation; sweep has a parent run plus independently cancellable per-meeting children. A cancelled sweep does not schedule another pass.

## Contract for #30 (Journal cancellation)

`snapshot()` returns immutable snapshots with a run UUID, canonical meeting URL if applicable, kind/stage, and `waiting`, `running` or `cancelling` state. Use a snapshot UUID with `cancelAndWait(id)` to cancel exactly that generation. `cancelAndWait(session:)` takes the matching generations present at the call; it does not target a later run. Repeated cancellation is harmless. Waiting queue reservations can be removed before starting; started work remains visible while unwinding and releasing claims and engines.

Retained snapshots also carry a completion handle and a per-session generation fence. `cancelAndWait(snapshot)` returns `.completed`, `.cancelled`, or `.failed(message)` after cleanup, even when the entry has already disappeared. A cancellation request does not turn a normal successful return into cancellation; owners that persist errors report them through `reportFailure`. Weak per-session generation storage retains no history of past outcomes. A later run invalidates an older Journal outcome even if the new run starts and finishes between UI polls. Multiple runs captured in one snapshot can still be cancelled together.

Journal captures all matching run IDs synchronously on click and shows Cancelling / Отменяется until they finish. Changing selection, closing the window, or clicking again cannot redirect that request. The actual terminal result is shown only for the captured meeting/generation; new runs discard old display state. General nil-session work and independently running CLI claims never enable the action.

Call cancellation/wait methods from an external owner, never inside the same operation. Native inference and synchronous conversion must return safely before cleanup. Cancellation preserves source audio, finished versions, prior summaries and per-run requests; it spends no failure attempts and does not immediately requeue the meeting in the same drain. Explicit retry or later recovery remain possible.

## Children and shared resources

Native engines keep their current cancellation callbacks and dedicated execution lanes. An operation awaits inference, then engine release, before finishing. Detached audio conversion is awaited even where it cannot stop mid-call. Import forwards cancellation to its hashing and normalization tasks and awaits them before removing staging. LLM command execution uses `Subprocess.run`, which waits for the launched process to exit after terminate/kill and cleans its temporary files; user-supplied `on_stop` commands use the same awaited runner with their original meeting working directory and arguments. The direct command must exit before its operation completes. An accepted hook stays marked fired on cancellation to avoid duplicating external side effects. Its standard input is closed. Awaiting the hook is a deliberate change from fire-and-forget: a long hook holds the session claim and delays the next queued transcription or direct diarization until it exits or is cancelled. A hook that invokes a Verbemo CLI writer for the same meeting receives a busy claim; recording/live and other independent operations remain separate. Command authors own any descendant processes their commands launch; the runner controls the directly launched process, including its terminate/kill/wait sequence. Captured output is bounded by the existing 32 MiB runner limit; output from a cancelled command is not forwarded.

Model stores own shared download flights. Cancelling one operation stops that consumer's wait; it must not cancel downloads still needed by another consumer. A flight with no consumers follows the store's cancellation/cleanup contract; this registry does not take ownership of shared model caches, separately requested settings downloads, calendar/metadata reads, or UI scans. Those do not write a meeting pipeline result and must not be mistaken for an active meeting operation. Shutdown separately stops the auto-record/network/config timers, library scans, playback, calendar picker, pending deletion and UI download consumers. It awaits resource-bearing UI tasks and committed Finder recycling after processing cleanup. OS-owned permission replies do not gate exit and cannot reopen settings after shutdown starts.

Windows ownership is unchanged. Native/runtime acceptance and its limitations are recorded separately from these ownership contracts in docs/testing.
